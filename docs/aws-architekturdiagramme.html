SZENARIO 2

Bestellprozess mit Saga und dreifacher Idempotenz

Eine API nimmt Bestellungen an. Zahlung, Lager und Versand arbeiten entkoppelt; jeder Schritt muss nachvollziehbar, wiederholbar und gegen Doppelverarbeitung geschützt sein.

Die API speichert die Bestellung und antwortet sofort. Ein DynamoDB-Stream dient als Transactional Outbox und startet eine Step-Functions-Saga. Jede Fachdomäne hat eine eigene Queue, einen eigenen Worker und ein eigenes Konto. Die Saga orchestriert, die Domänen kennen sich gegenseitig nicht.

Diagramm seitlich verschieben, um alles zu sehen.

Nr.FlussWas passiert
1Client → CloudFrontPOST /orders über HTTPS mit Header Idempotency-Key (UUID, vom Client je Bestellung einmal erzeugt und bei Wiederholung gleich gesendet).
2WAF → API GatewayAWS WAF filtert mit Managed Rules und Rate-Based Rules; CloudFront leitet an den regionalen API-Endpunkt.
3API Gateway ↔ CognitoJWT-Authorizer prüft das Token, API Gateway validiert das Request-Schema. Ungültige Anfragen enden hier mit 401 oder 400.
4API Gateway → Order APILambda erzeugt die orderId, die ab jetzt in Logs, Traces und Events als Korrelations-ID mitläuft.
5Order API → IdempotenzSchreiben mit attribute_not_exists(key). Ist der Key schon vorhanden, kommt die gespeicherte Antwort zurück und es entsteht keine zweite Bestellung.
6Order API → OrdersBestellung mit Status PENDING. Schritt 5 und 6 laufen in einer TransactWriteItems, also ganz oder gar nicht. Antwort an den Client: 202 Accepted mit orderId.
7Stream → PipesDynamoDB Streams liefern jedes neue Item genau einmal pro Shard in Reihenfolge. EventBridge Pipes filtert auf INSERT und formt das Event OrderPlaced.
8Pipes → Event BusEvent landet auf dem Bus orders-bus; ein Archiv speichert alle Events für späteres Replay.
9Regel → Step FunctionsRegel startet die Saga mit Ausführungsname = orderId. Ein zweiter Start mit demselben Namen wird mit ExecutionAlreadyExists abgelehnt.
10Saga → Domänen-QueuesJeder Task schickt eine Nachricht mit Task-Token an die Queue der Domäne (waitForTaskToken, Heartbeat-Timeout gesetzt).
11Worker → DedupeWorker schreibt orderId#schritt bedingt in die Dedupe-Tabelle und führt den Schritt nur aus, wenn der Eintrag neu ist. Externe Aufrufe tragen einen eigenen Idempotency-Key.
12Worker → SagaSendTaskSuccess oder SendTaskFailure. Die Saga fährt fort oder springt in die Kompensation.
13Saga → OrdersStatus CONFIRMED oder FAILED wird gesetzt; das zugehörige Event geht an den Bus (Kundenbenachrichtigung, Analytics).
AnforderungUmsetzung
EntkoppeltJe Domäne eigene Queue, eigener Worker, eigene Datenhaltung. Fällt der Versand aus, puffert seine Queue; Zahlung und Lager laufen weiter.
NachvollziehbarAusführungshistorie je Bestellung in Step Functions, X-Ray-Trace von API bis Worker, strukturierte Logs mit orderId, Status in Orders, EventBridge-Archiv, CloudTrail für API-Aufrufe.
WiederholbarSQS-Redrive aus der DLQ, Step-Functions-Retry und Redrive ab dem fehlgeschlagenen Schritt, EventBridge-Replay aus dem Archiv. Das ist sicher, weil jeder Schritt idempotent ist.
Keine DoppelverarbeitungDrei Ebenen: Idempotency-Key an der API, eindeutiger Ausführungsname der Saga, Dedupe-Tabelle je Schritt. Dazu der Idempotency-Key beim Zahlungsanbieter, damit nie doppelt belastet wird.
Fehlerpfade
  • Transienter Worker-Fehler: Nachricht wird nach dem Visibility-Timeout erneut zugestellt. Nach 5 Versuchen geht sie in die DLQ, ein Alarm meldet jede Nachricht dort, Redrive nach dem Fix.
  • Timeout oder fehlender Heartbeat: Step Functions wiederholt den Task 3-mal mit exponentiellem Backoff und Jitter, danach greift Catch.
  • Fachlicher Fehler: Lager leer → direkt FAILED. Zahlung abgelehnt → Reservierung freigeben → FAILED. Versand unmöglich → Zahlung erstatten → Reservierung freigeben → FAILED.
  • Zustellung an Ziele: EventBridge-Regel und Pipe haben eigene Retry-Policies und eine DLQ, damit kein Event verloren geht.
  • Duplikate: gleicher Key → gespeicherte Antwort; doppeltes Event → ExecutionAlreadyExists; doppelte SQS-Zustellung → Dedupe-Treffer, Worker meldet nur das gespeicherte Ergebnis.
Sicherheitsgrenzen
  • Öffentliche Kante nur über CloudFront mit WAF, TLS und Cognito-JWT. API Gateway akzeptiert nur Aufrufe über CloudFront.
  • Jede Domäne in eigenem Konto bzw. mit eigener IAM-Rolle: ein Worker darf nur die eigene Queue lesen und SendTask* nur für diese eine State Machine aufrufen.
  • Zahlung im PCI-Scope; das Credential für den Zahlungsanbieter liegt in Secrets Manager und rotiert automatisch.
  • Verschlüsselung mit KMS für DynamoDB, SQS, EventBridge und Logs; Queue-Policies erlauben nur die Rolle der State Machine.
Skalierungsgrenzen
  • Throttling und Usage Plans an API Gateway schützen das Backend vor einzelnen Clients.
  • SQS puffert Lastspitzen je Domäne. Reserved Concurrency am Zahlungs-Worker hält das Ratenlimit des Zahlungsanbieters ein.
  • DynamoDB im On-Demand-Modus. Bei sehr hohem Bestellvolumen die StartExecution-Quotas von Step Functions prüfen und den Start über eine Queue glätten.
SZENARIO 3

Produktions-Remediation nach fehlerhaftem Deployment

Ein Deployment erhöht 5xx-Rate und Latenz. Gezeigt werden Erkennung, Ereignisvermittlung, Diagnose und Entscheidung, Rollback und Benachrichtigung einschließlich Sicherheitsgrenzen.

Es gibt zwei Wege zurück zur letzten guten Version. Solange das Deployment noch läuft, rollt CodeDeploy selbst zurück, sobald der Alarm auslöst. Fällt der Fehler erst nach dem Deployment auf, startet im separaten Operations-Konto ein Workflow, der diagnostiziert, nach festen Regeln entscheidet und nur innerhalb enger Leitplanken selbst handelt.

Diagramm seitlich verschieben, um alles zu sehen.

Nr.FlussWas passiert
1CodePipeline → CodeDeployECS Blue/Green mit Canary 10 % für 5 Minuten. Die CloudWatch-Alarme sind an die Deployment-Gruppe gebunden, Auto-Rollback ist aktiv.
2CodeDeploy → ALBTraffic-Shift über den Listener von Blau (v1) auf Grün (v2).
3ECS/ALB → CloudWatchHTTPCode_Target_5XX_Count, RequestCount, TargetResponseTime (p99), Logs und X-Ray-Traces.
4Synthetics → AlarmCanary prüft den Checkout-Pfad jede Minute und liefert SuccessPercent.
5Metriken → Composite AlarmMetric Math: 5xx-Rate > 2 % und p99 > 800 ms in 3 von 5 Minuten. Zwei unabhängige Signale verringern Fehlalarme. Schwellwerte sind Beispielwerte.
6Alarm → CodeDeploySchneller Pfad: Läuft das Deployment noch, stoppt CodeDeploy es und schaltet den Traffic auf Blau zurück.
7Alarm, CodeDeploy → Standard-BusCloudWatch Alarm State Change und Deployment-Events landen auf dem Standard-Bus des Workload-Kontos.
8Standard-Bus → Ops-BusKontoübergreifende Regel. Die Resource Policy des Ops-Busses akzeptiert nur Events aus den freigegebenen Workload-Konten.
9Ops-Bus → Step FunctionsRegel auf state = ALARM für Produktions-Services startet den Remediation-Workflow. Fehlschläge bei der Zustellung gehen in die Regel-DLQ.
10Lock setzenBedingtes Schreiben je Service mit TTL 60 Minuten. Ist der Lock belegt, wird nur benachrichtigt. So gibt es höchstens einen automatischen Eingriff je Service und Stunde.
11DiagnoseLiest über CloudWatch Cross-Account Observability (OAM) nur lesend: letztes Deployment mit Zeit und Version, Top-Fehler aus Logs Insights, fehlerhafte Knoten aus X-Ray.
12EntscheidungAutomatisch nur, wenn das Deployment höchstens 30 Minuten alt ist, die Fehler auf die neue Version konzentriert sind und die vorige Version als gesund bekannt ist. Sonst entscheidet ein Mensch.
13RollbackSSM Automation übernimmt die Remediation-Rolle im Workload-Konto und setzt den ECS-Service auf die vorige Task-Definition.
14Freigabe durch On-CallAnfrage über SNS in den Chat-Kanal (Amazon Q Developer in chat applications). Die Freigabe ruft SendTaskSuccess auf; ohne Antwort nach 15 Minuten wird eskaliert.
15Verifizieren5 Minuten warten, dann den Alarmstatus erneut lesen.
16Abschluss oder EskalationAlarm OK → Lock freigeben, Bericht in den Chat. Weiter ALARM, Ablehnung oder ein fehlgeschlagener Task → Incident Manager pagt On-Call. Danach keine weitere Automatik.
Fehlerpfade
  • Event nicht zustellbar: Retry-Policy der Regel, danach Regel-DLQ mit eigenem Alarm.
  • Task schlägt fehl: Jeder Task hat Retry für transiente Fehler und Catch auf „Eskalieren“.
  • Rollback hilft nicht: Verifikation findet weiter ALARM → Eskalation, kein zweiter automatischer Versuch.
  • Mensch antwortet nicht: Task-Token-Timeout nach 15 Minuten → Eskalation an die nächste Stufe.
  • Workflow läuft schon: Lock belegt → nur Benachrichtigung, kein paralleler Eingriff.
Sicherheitsgrenzen
  • Remediation läuft im eigenen Operations-Konto. Im Workload-Konto gibt es nur eine Rolle mit ecs:UpdateService und codedeploy:StopDeployment auf die ARN dieses Service.
  • Diagnose ist rein lesend über OAM. Löschen, Scale-in und Änderungen an Netzwerk oder IAM sind per Permission Boundary und SCP ausgeschlossen.
  • Rollback nur auf die vorige, gesund gemeldete Version, höchstens einmal je Service und Stunde, nie während eines Change Freeze ohne Freigabe.
  • CloudTrail protokolliert jede Aktion der Rolle; der Bericht nennt Ausführungs-ARN und Entscheidungsgrund.
Skalierungsgrenzen
  • Service Auto Scaling (min 4, max 40 Tasks) bleibt aktiv, ersetzt aber keinen Rollback: Scale-out verdeckt einen Code-Fehler nur.
  • Der Lock begrenzt die Automatik auf einen Workflow je Service. Bei vielen Services gleichzeitig deutet das auf ein Plattformproblem hin, dann wird sofort eskaliert.
  • Der Canary-Anteil von 10 % begrenzt den Schaden während des Deployments auf einen Teil der Nutzenden.

Alle Schwellwerte, Zeiten und Grenzen sind Beispielwerte für die Übung. Konkrete Service-Quotas hängen von Region und Konto ab und sollten in der AWS-Dokumentation bzw. in Service Quotas geprüft werden.
